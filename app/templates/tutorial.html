1. The Basics of Real-Time Bidding

Real-Time Bidding (RTB) represents a sub-millisecond, automated programmatic auction where publisher ad space is traded on a per-impression basis while a page is loading.

🚗 The Digital Billboard Analogy Think of a smart digital billboard on a highway. Every time a car passes, the billboard instantly scans key characteristics (speed, time of day, approximate direction) and decides what ad to show. Behind the scenes, multiple advertisers bid for that specific passing car. The highest bid wins and is displayed instantly.

The Programmatic Supply Chain

Programmatic advertising relies on three key transactional nodes to complete an auction:

1. Publisher / App

Owns the digital inventory (e.g. news page, CTV app stream) and requests an ad.
➔

2. Ad Exchange / SSP

Conducts the auction, parses device context, broadcasts requests, and selects the winner.
➔

3. DSP / Bidder

Analyzes auction contexts on behalf of advertisers and submits competitive bids.

Transport & Protocols

HTTP POST Transport

All bid requests are sent via HTTP POST to accommodate large structured payloads and potential binary serialization (Protobuf or Avro).

Connection Persistence

Exchanges and bidders use Keep-Alive (Persistent Connections) to eliminate TCP handshake overhead and decrease latency.

Compression (Gzip)

Payloads are compressed with gzip. Bidders signal gzip acceptance via the Accept-Encoding header and exchanges compress requests using Content-Encoding.

2. Core Object Model & Fields

To avoid auction discrepancies, OpenRTB requires strict conformance to object models on both request and response payloads.

Key BidRequest Properties

Field Path Type Description & Status
id string Unique identifier for this auction Required
imp array Array of impression opportunities (at least one) Required
imp[].id string Unique identifier for the impression slot Required
imp[].bidfloor float CPM minimum floor price in the declared currency Recommended
site object Content details for browser-based web inventory Recommended
app object Content details for mobile app or CTV inventory Recommended
⚠️ Crucial Schema Anti-Pattern A single bid request must **never** contain both a site and an app object. If both are specified, the inventory context is ambiguous and the request will be flagged as invalid.

Key BidResponse Properties

Field Path Type Description & Status
id string Must match the originating BidRequest ID Required
seatbid array Collection of seat bids (representing advertisers) Required
seatbid[].bid array Collection of actual bids for the placement slots Required
seatbid[].bid[].impid string Must map to the respective imp.id Required
seatbid[].bid[].price float Bidded CPM price in the declared currency Required

3. CTV Ad Pods & Channels OpenRTB 2.6

OpenRTB 2.6 introduces native support for **Ad Pods**, enabling linear TV-style ad breaks in video and audio streams.

Structured Pods

The seller provides a fully static ad break. The number of slots, their sequence, and their durations are pre-defined (e.g. 4 slots of 30 seconds each).

Dynamic Pods

The seller sets the total pod duration and maximum sequence limits, but allows the bidder to define individual creative durations (e.g., filling 120s with up to 4 ads of 15s or 30s).

Hybrid Pods

A mix of static structured slots and flexible dynamic slots in the same ad break.

Pod-Specific Heuristics

  • Mutual Exclusion of Duration: Sellers must include **either** rqddurs (exact acceptable durations) or the minduration/maxduration parameters, but never both.
  • CPM-per-Second Floor (mincpmpersec): Used in dynamic pods to prevent bidders from filling breaks with low-CPM, high-duration ads. Floor value scales relative to the creative duration.
  • Guaranteeing Slot Placement: Bidders should avoid supplying slotinpod in bid responses for structured pods, as the impid uniquely maps to the slot. slotinpod (e.g., 1=first, -1=last) should only be used to specify premium slot targeting in dynamic pods.

Network vs Channel Hierarchy

Differentiating content distribution layers is crucial in CTV context. 2.6 formalizes two objects:

  • App (or Network): Discovery+

4. Structured User Agent & Privacy OpenRTB 2.6

Modern browsers and platforms are freezing or deprecating the traditional User-Agent string. OpenRTB 2.6 introduces objects for reliable identity and privacy signals.

Structured User-Agent (device.sua)

Instead of relying on parsing complex user-agent strings, 2.6 standardizes the device.sua object:

"sua": {
  "browsers": [
    { "brand": "Chrome", "version": ["100", "0", "4896", "127"] }
  ],
  "platform": { "brand": "Windows", "version": ["10", "0", "0"] },
  "mobile": 0,
  "architecture": "x86",
  "model": "PC"
}

Privacy & Regulations

OpenRTB supports multiple legal compliance frameworks. Flagged in the regs and device objects:

COPPA (regs.coppa)

Child Online Privacy Protection Act. Set to 1 if the traffic is subject to child privacy rules.

GDPR (regs.ext.gdpr)

General Data Protection Regulation. Flagged to signal European privacy applicability.

GPP (regs.gpp / gpp_sid)

Global Privacy Platform. OpenRTB 2.6 recommends specifying **both** the gpp consent string and the gpp_sid section IDs array.

5. Counting Methodologies & No-Bid Signaling

Accurately counting billable events is critical for programmatic accounting and discrepancy resolution.

MRC-Aligned Impression Counting

Methodology Application Best Practices & Limitations
Pixel in Markup Display Ads (Web) Original web standard. Overcounts on mobile apps since creatives are pre-fetched before display.
VAST <Impression> Video & Audio Fired from the client player upon creative play start. Required for all video/audio streams.
Billing Notice (burl) All formats (except Video) DSP-supplied URL. Fired by the exchange server-to-server as close to the billing event as possible.
Win Notice (nurl) Troubleshooting only Signals auction win only. **Should never be used for billing** because won ads are often not rendered.
🔒 Server-Side Firing Best Practices When firing billing notifications (burl) from servers:
  • Include the X-Forwarded-For header indicating the end-user device IP.
  • Include the X-Device-User-Agent header indicating the end-user browser agent.
  • Sign requests cryptographically via ads.cert to prevent billing fraud.

No-Bid Responses

Bidders can decline to bid in four different ways. OpenRTB 2.6 formalizes the use of No-Bid Reasons (nbr):

  1. HTTP 204 "No Content": Most efficient, saves bandwidth.
  2. Empty JSON: Returning {}.
  3. Empty SeatBid: Returning {"id": "req-1", "seatbid": []}.
  4. Explicit No-Bid: Returning {"id": "req-1", "seatbid": [], "nbr": 2} (where 2 = Invalid Request, 4 = Suspected NHT).
